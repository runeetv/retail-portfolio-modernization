# Hands-On Tutorial: AI-Assisted Legacy Application Modernization with Kiro

Reverse-engineer three legacy .NET applications, rebuild their business architecture from evidence, grade the result against an answer key, and forward-engineer them into one modern web application, all driven by Kiro.

<!-- pagebreak -->

## About this tutorial

This tutorial walks you through a complete legacy modernization: three separate legacy applications (a Windows desktop app, a server-rendered web portal, and a REST API) all sharing one SQL Server database become a single modern ASP.NET Core web application. The journey runs in six stages. Each stage is driven by a carefully written prompt that you run in **Kiro**.

The repository you received contains everything you need:

- The **legacy application portfolio** (source code, database schema, stored procedures, seed data, tests).
- The **prompts** for every stage (`Prompts/`).
- A **reference run**: the artifacts and the final application produced when this method was first run. You will use it to compare against your own results.
- A **withheld answer key** (`benchmark/ground-truth/`) used to measure how accurately the AI reconstructed the legacy system.

### What you will learn

- How to break a modernization into isolated, evidence-driven stages that an AI agent can run reliably.
- How to reverse-engineer business capabilities, entities, rules, workflows, and data dependencies from code, not from documentation or assumptions.
- How to measure the accuracy of AI-generated analysis against a ground truth before trusting it.
- How to turn verified findings into a consolidation specification with full functional traceability.
- How to have Kiro build, test, and validate the consolidated application against that specification.

### What you will end up with

- Your own set of analysis, evaluation, and planning artifacts, generated by Kiro.
- A working **UnifiedRetail** ASP.NET Core (.NET 10) web application with customer, staff, and warehouse areas plus a backward-compatible API, running over the original database.
- A scorecard showing how accurate your Kiro run was, side by side with the reference run.

### Time required

Plan for roughly **one to two working days** end to end. Stages 1 through 4 are analysis and planning and typically take tens of minutes each in Kiro. Stage 5 (the application build) is the longest stage and can take several hours of agent time. Actual times depend on the model you choose in Kiro and how much you review between steps.

> **IMPORTANT — Kiro is the operative tool for this exercise.** Every stage of this tutorial is executed by the Kiro AI agent. Kiro reads the code, runs the build and test commands, writes the artifacts, and implements the new application. Without Kiro you can still read the reference artifacts, but you cannot perform the exercise. Install and sign in to Kiro before you begin (see Module 1).

## Kiro: the operative tool

### What Kiro is

**Kiro** (https://kiro.dev) is an agentic AI development environment (IDE) from AWS. Besides editing code, Kiro's built-in AI agent can read an entire repository, reason across many files, run terminal commands (such as `dotnet build` and `dotnet test`), create and edit files, and iterate until a task is done. Kiro is available for Windows, macOS, and Linux.

### Why this exercise depends on Kiro

| Modernization need | What Kiro provides |
|---|---|
| Read and trace thousands of lines of C#, XAML, Razor, and SQL across many projects | The agent explores the workspace, follows call paths, and cites the files and symbols it used |
| Produce many structured artifacts (YAML catalogs, Markdown reports, Mermaid diagrams) per stage | The agent writes files directly into the workspace in the folder structure each prompt requires |
| Verify findings by running code | The agent runs builds, tests, and scripts in the integrated terminal (with your approval) and reports the real results |
| Build a full application incrementally | The agent implements milestone by milestone, builds and tests after each one, and fixes failures |
| Keep you in control | You approve commands, review diffs, and can roll back changes. Each stage runs in a fresh chat session you start |

### Kiro concepts used in this tutorial

This tutorial uses **Kiro IDE agent chat in Vibe mode**: you start a chat session, paste a stage prompt, and let the agent work. The concepts below are all you need. (Kiro's UI changes over time; if a label differs slightly in your version, look for the equivalent control.)

| Concept | How it is used here |
|---|---|
| **Chat panel** | Where you paste each stage prompt and watch the agent work |
| **Vibe session** | A conversational agent session. Start a **new session for every stage** so earlier context does not leak into later stages |
| **Autopilot / Supervised** | Autopilot lets the agent make file changes without asking for each one; Supervised lets you review changes as they happen. Supervised is recommended for your first run of each stage |
| **Command approval** | Before the agent runs a terminal command, Kiro asks for approval. You can trust specific commands (for example `dotnet build`, `dotnet test`) to reduce prompts |
| **Context with #** | Typing `#` in chat attaches context, such as `#Folder` or `#File`. Use it to point the agent at the folders a stage is allowed to see |
| **Model selection** | Choose the model the agent uses. A strong reasoning model is recommended for these long, multi-file tasks |
| **Checkpoints / revert** | If a session goes wrong, revert the agent's changes and rerun. Git commits after every stage give you a second safety net |

## The scenario: a legacy retail portfolio

A fictional retailer runs three applications, built by different teams over several years. All three read from and write to one SQL Server database called `LegacyRetailDB`.

| Application | Technology | Users | Responsibility | Source |
|---|---|---|---|---|
| **OrderDesk** | WPF desktop app (C#, XAML, MVVM), .NET 10 | Sales and customer-service staff | Customers, sales quotes, discount approvals, staff orders, cancellations with override, return review, sales-agent tasks and commissions | `src/OrderDesk` |
| **CustomerPortal** | ASP.NET Core MVC with Razor views, .NET 10 | Customers | Sign-in, profile, catalog, cart, coupons, idempotent checkout, order history, cancellation, returns, tracking, support tickets, wishlist | `src/CustomerPortal` |
| **FulfillmentAPI** | ASP.NET Core Web API with Swagger, .NET 10 | Warehouse systems | Inventory allocation, picking, packaging, dispatch, carrier events, return receipt and restocking, warehouse reporting | `src/FulfillmentAPI` |

The database (`database/`) has 40 tables, 5 stored procedures that hold real business rules, and a deterministic seed of more than 100 customers, 120 products, and 240 orders.

### Why this portfolio is a realistic test

The portfolio was built on purpose to look like real enterprise software, with the kinds of problems that make modernization hard:

- Each app has **its own C# model of shared tables** (for example, three different `Order` classes over `dbo.Orders`).
- Some business rules are **duplicated** across apps; others are **implemented differently** on purpose (for example, staff and customers have different cancellation rules).
- Some rules live in **C# services**, others in **SQL stored procedures**.
- The apps never call each other. They are **coupled only through the shared database**.
- Similar names do not always mean the same thing (for example, `Customer` and `CustomerAccount` are different concepts).

A good modernization must discover all of this, keep the differences that matter to the business, and lose no functionality.

> **Note on language:** the legacy applications are written in C#. The same staged method applies unchanged to VB.NET, ASP.NET Web Forms, or other legacy stacks. See "Applying the method to your own codebase" at the end of this tutorial.

### The target

One deployable **ASP.NET Core .NET 10 modular monolith**, called **UnifiedRetail**, that:

- Serves a **customer storefront**, a **staff area** (replacing the WPF desktop app), and a **warehouse area**.
- Preserves all 15 existing `/api/fulfillment/*` endpoints for backward compatibility.
- Implements all 47 discovered business capabilities.
- Runs on the **unchanged** database schema and stored procedures.

## The six-stage method

| Stage | Name | Goal | Prompt(s) | Output folder |
|---|---|---|---|---|
| 0 | Pre-Work | Build the legacy portfolio and the ground-truth answer key (already done for you) | `01.CreateDemoApps.md`, `02.GroundTruthBuilder..md` | `src/`, `database/`, `benchmark/ground-truth/` |
| 1 | Reverse-engineer each app separately | Rebuild each app's capabilities, entities, rules, workflows, and DB dependencies from code only | `03.OrderDesk.md`, `04.CustomerPortal.md`, `05.FullfillmentAPI.md` | `analysis-output/<app>/` |
| 2 | Semantic reconstruction | Merge the three analyses into one portfolio view, then verify every relationship against source | `06. SementicReconsutuction.md` | `analysis-output/portfolio/` |
| 3 | Ground-truth evaluation | Score the reconstruction against the withheld answer key with deterministic metrics | `07.GroundTruth.md` | `evaluation-output/` |
| 4 | Consolidation requirements and target design | Turn verified findings into an approved specification. No code yet | `08.ConsolidationRequirmentsAndTargetDesign.md` + `07.5GroundTruth2.md` (add-on) | `consolidation-planning/` |
| 5 | Application build | Implement, test, and validate the unified application | `09.BuildTheApp.md` | `consolidated-app/` |

### Principles that make the method work

1. **Evidence over assumption.** Every finding must cite a real file, class, method, or SQL object. Findings are labelled `static_verified` (source inspected), `behavior_verified` (test executed), or `inferred`.
2. **Isolation before integration.** Each application is analyzed alone first, so the agent cannot "guess" from the other apps. Cross-application conclusions come only in Stage 2.
3. **Measure before you trust.** Stage 3 grades the AI's analysis against a ground truth before anything is built on it.
4. **Nothing is silently discarded.** Every capability gets an explicit disposition and a parity test in Stage 4.
5. **Preserve legitimate differences.** Different rules for different actors are kept as explicit policies, not "fixed".
6. **Human gates.** You review and approve the output of every stage before starting the next.

## Module 2: Prepare a clean learner workspace

The repository already contains the reference run's outputs, the answer key, and the original design specification. If Kiro can see them while it works, it can copy answers instead of discovering them, and your experiment would be meaningless. In this module you will:

1. Keep a **read-only reference copy** of everything, outside your Kiro workspace.
2. Create a **learner branch** where the generated outputs, answer key, and design-spec prompts are removed.

### 2.1 Create your learner branch and the reference copy

From the repository root:

```powershell
# 1. Your working branch
git checkout -b my-modernization-run

# 2. A second, read-only checkout of 'main' next to your workspace.
#    Do NOT open this folder in Kiro.
git worktree add ../modernization-reference main
```

You now have `../modernization-reference/` containing the original prompts, reference outputs, and ground truth. You will copy prompts from it and compare your results against it.

### 2.2 Strip the learner branch down to the legacy code

```powershell
# Remove the reference outputs (Kiro will regenerate them)
git rm -r -q analysis-output evaluation-output consolidation-planning consolidated-app

# Withhold the answer key, the design spec, and the reference narrative from the agent
git rm -r -q benchmark Prompts ModernizationStep.md docs/tutorial

git commit -m "Learner run: start from legacy code only"
```

> **Why also remove the prompts and this tutorial?** The Stage 0 prompt (`01.CreateDemoApps.md`) is the original design specification and lists the deliberate overlaps and traps. This tutorial quotes reference results. Kiro must not read either during Stages 1 and 2. You will paste each stage prompt from `../modernization-reference/Prompts/` instead.

Your workspace now contains only what a real modernization team would have: `src/`, `database/`, `tests/`, `docs/`, `scripts/`, the solution file, and `README.md`.

> **Tip:** `docs/IMPLEMENTATION-PROGRESS.md` and `docs/ARCHITECTURE.md` are ordinary project documentation, like what a real legacy system might have. They are allowed inputs.

### 2.3 Optional: give Kiro trusted commands

To avoid approving the same safe commands over and over, trust read-only and build/test commands when Kiro first asks (for example `dotnet build`, `dotnet test`, `git status`, `git diff`). Keep approval on for anything that deletes files, resets the database, or touches anything outside the workspace.

## Module 3: How to run a stage in Kiro (repeat for every stage)

Every stage follows the same eight-step loop. Learn it once and then apply it to each stage.

1. **Start a new Vibe session** in the Kiro chat panel. Never continue a previous stage's session, because it carries context that could break isolation.
2. **Open the stage prompt** from `../modernization-reference/Prompts/<stage folder>/<file>.md` in any text editor and copy its full contents.
3. **Paste the prompt** into the Kiro chat. Optionally attach the allowed inputs with `#Folder` (for example `#Folder src/OrderDesk`), to reinforce the scope.
4. **Choose Supervised** for your first run of a stage (to review changes), or **Autopilot** once you trust the flow.
5. **Approve commands** as Kiro asks to run builds, tests, or scripts. Read each command before approving it. Decline anything that resets the database or touches folders outside the stage's scope.
6. **Let the agent finish.** If it stops early, reply with `Continue. Complete all remaining deliverables listed in the prompt.`
7. **Review the output** using the stage's checklist in this tutorial, then commit:

   ```powershell
   git add -A
   git commit -m "Stage N: <description>"
   ```

8. **Compare with the reference run** (see 3.1).

### 3.1 Comparing your results with the reference

Because your branch started from `main`, git can compare any folder of your run with the reference:

```powershell
# Which files differ, and how much
git diff main --stat -- analysis-output/orderdesk

# Full diff of one artifact
git diff main -- analysis-output/orderdesk/capabilities.yaml
```

You can also open both versions side by side in Kiro's editor: your file in the workspace, and the reference in `../modernization-reference/`.

> **Do not expect identical text.** AI output varies between runs. Compare **substance**: did your run find the same capabilities, rules, entities, and traps? Did it cite real evidence? Are the IDs consistent across files?

### 3.2 Quick validity checks you can run after any stage

```powershell
# Every YAML file in the stage's output folder parses (requires: pip install pyyaml)
python ../modernization-reference/docs/tutorial/tools/validate_yaml.py analysis-output
```

You can also ask Kiro in the same session: *"Validate that every YAML file you produced parses with a strict YAML parser, and that every source path you cited exists. Fix any failures."*

> **Why this matters:** the most common slip is an unquoted `?` inside a YAML list, such as `decision_points: [locked?, password valid?]`. Even the reference run has a few files with this problem (for example `analysis-output/*/workflows.yaml`). Ask Kiro to quote such values.

- [ ] All 9 files (10 for FulfillmentAPI) exist and every YAML file parses.

## Stage 2: Semantic reconstruction (portfolio view)

**Goal:** combine the three independent analyses into one portfolio model: canonical capabilities, how capabilities relate across apps, canonical domains and entities, cross-app dependencies and workflows. Then verify every proposed relationship against the source.

**Prompt:** `Stage 2. Semenatic Reconstruction/06. SementicReconsutuction.md`

### Steps

1. Start a **new Vibe session**.
2. Paste the prompt. It runs in two phases:
   - **Phase A, Semantic consolidation:** uses only `analysis-output/{orderdesk,customerportal,fulfillmentapi}/`.
   - **Phase B, Source-level verification:** inspects all three codebases, the SQL, and tests to confirm, revise, or reject each Phase A relationship.
3. If Kiro tries to go straight to source code, remind it: *"Complete Phase A from the Stage 1 outputs only and save the candidate findings before starting Phase B."*
4. Review, commit (`Stage 2: portfolio reconstruction`), and compare.

### Relationship vocabulary used

| Class | Meaning |
|---|---|
| `duplicate` | Substantially equivalent functionality |
| `partial_overlap` | Same capability, different responsibilities, scope, or rules |
| `complementary` | Different capabilities that contribute to one business process |
| `shared_data_only` | Shared data, no significant functional overlap |
| `unique` | Belongs to one application |

### Expected deliverables

```text
analysis-output/portfolio/
├── portfolio-capabilities.yaml
├── capability-overlaps.yaml
├── canonical-domains.yaml
├── cross-app-dependencies.yaml
├── cross-app-workflows.yaml
├── business-rule-comparison.yaml
├── portfolio-architecture.md     # capability map, matrices, Mermaid diagrams
├── evidence-index.yaml
└── unresolved-findings.md
```

### What good output looks like (reference excerpt)

From the reference `analysis-output/portfolio/capability-overlaps.yaml`:

```yaml
  - id: OVL-CUSTOMER
    capability: PF-CAP-CUSTOMER-MANAGE
    relationship: partial_overlap
    apps: [APP-ORDERDESK, APP-PORTAL, APP-FULFILL]
    rationale: >
      OrderDesk edits the full contact/shipping record; CustomerPortal edits only a
      self-service subset (phone + shipping); FulfillmentAPI only counts distinct
      customers inside a report. Same physical table (dbo.Customers) via different
      C# models; not duplicate functionality.
    verification: static_verified
    evidence:
      source:
        - src/OrderDesk/OrderDesk.Application/CustomerService.cs#UpdateContactAsync
        - src/CustomerPortal/CustomerPortal.Application/ProfileService.cs#UpdateSelfServiceAsync
        - database/procedures/procedures.sql#usp_WarehouseActivitySummary
```

### Review checklist

- [ ] Original Stage 1 IDs are preserved for traceability.
- [ ] No relationship is marked `duplicate` just because two apps use the same table or class name.
- [ ] Shared tables with several C# models are identified (for example, three `Order` models over `dbo.Orders`).
- [ ] `Customer` and `CustomerAccount` are kept as **distinct** concepts.
- [ ] The staff vs customer **cancellation difference** is recorded as a legitimate, bounded divergence.

  Customer rule, in C# (`src/CustomerPortal/CustomerPortal.Domain/PortalRules.cs`):

  ```csharp
  public static bool CustomerCanCancel(string orderStatus) =>
      orderStatus is "Pending" or "Confirmed";
  ```

  Staff rule, in SQL (`usp_EvaluateCancellationEligibility`):

  ```sql
  ELSE IF @Status IN ('Pending','Confirmed','Allocated')
      SET @IsEligible = 1; SET @Reason = 'Eligible for staff cancellation.';
  ```

- [ ] Coupling is described as **data-mediated** through the shared database. There are no invented API calls between apps.
- [ ] Phase A hypotheses that could not be verified are listed in `unresolved-findings.md`, not silently promoted.

## Stage 3: Ground-truth evaluation

**Goal:** measure how accurate Stages 1 and 2 were, using the withheld answer key and deterministic, code-computed metrics, **before** anything is built on top of them.

**Prompt:** `Stage 3. GroundTruth/07.GroundTruth.md`

### Steps

1. **Reveal the answer key** to the workspace (for this stage only):

   ```powershell
   Copy-Item -Recurse ../modernization-reference/benchmark ./benchmark
   ```

2. Start a **new Vibe session** and paste `07.GroundTruth.md`. Kiro acts as an independent evaluator: it matches every ground-truth item to a prediction (`exact`, `partial`, `incorrect`, unmatched, or `ambiguous`), freezes those decisions in YAML match tables, and writes `score.py` to compute the metrics.
3. When Kiro asks to run the scorer, approve it. You can also run it yourself:

   ```powershell
   python evaluation-output/score.py
   ```

4. Review the results, then **hide the answer key again** before Stage 4 so planning is based on your findings, not the answers:

   ```powershell
   Remove-Item -Recurse -Force ./benchmark
   git add -A
   git commit -m "Stage 3: ground-truth evaluation"
   ```

### Scoring model

| Category | Weight | Unit |
|---|---|---|
| Business capability discovery | 25% | ground-truth capability (27) |
| Domain and entity discovery | 20% | physical table (40) + multi-model traps |
| Overlap classification | 20% | overlap scenario (6) |
| Business-rule discovery | 15% | ground-truth rule (19) |
| Cross-app dependencies | 10% | dependency edges and stored procedures |
| Evidence accuracy | 10% | sampled evidence references |
| Workflows | diagnostic | cross-app workflows |

Two metric families are reported: **strict** (only `exact` counts) and **partial credit** (`exact` = 1.0, `partial` = 0.5).

### Expected deliverables

### Code walkthrough: how the reference build preserved behavior

**1. Reuse proven business logic instead of rewriting it.** The reference host references the existing domain, application, and infrastructure projects and registers their services. The real rules, EF mappings, and stored-procedure calls therefore run unchanged (`consolidated-app/src/UnifiedRetail/Program.cs`):

```csharp
// Persistence (provisional PoC decision): reuse the three proven per-app DbContexts
// over the ONE shared LegacyRetailDB connection.
builder.Services.AddDbContextFactory<OrderDeskDbContext>(o => o.UseSqlServer(connectionString));
builder.Services.AddDbContext<PortalDbContext>(o => o.UseSqlServer(connectionString));
builder.Services.AddDbContext<FulfillmentDbContext>(o => o.UseSqlServer(connectionString));

// Application services reused verbatim from the three source apps
builder.Services.AddScoped<OrderDesk.Application.QuoteService>();
builder.Services.AddScoped<CustomerPortal.Application.CheckoutService>();
builder.Services.AddScoped<FulfillmentAPI.Application.AllocationService>();
// ...
```

**2. Thin compatibility controllers: one business core, two surfaces.** The preserved API and the new warehouse UI call the **same** application services (`Modules/Fulfillment/Api/CompatibilityControllers.cs`):

```csharp
[ApiController]
[Route("api/fulfillment/orders")]
public class OrdersController : FulfillmentControllerBase
{
    private readonly FulfillmentQueryService _query;
    public OrdersController(FulfillmentQueryService query) => _query = query;

    [HttpGet("pending")]
    public async Task<IActionResult> GetPending(CancellationToken ct)
        => Ok(await _query.GetPendingOrdersAsync(ct));

    [HttpGet("{orderId:int}")]
    public async Task<IActionResult> Get(int orderId, CancellationToken ct)
    {
        var o = await _query.GetOrderAsync(orderId, ct);
        return o is null ? NotFound(new { error = "Order not found." }) : Ok(o);
    }
}
```

**3. Desktop to web.** The WPF OrderDesk screens (customers, quotes, approvals, orders, returns, agents) become the Razor views under `Areas/Staff/Views/`, backed by the same OrderDesk application services the desktop ViewModels used.

## Applying the method to your own codebase

The prompts are written for this portfolio, but the method is general. To use it on your own legacy system (C#, **VB.NET**, ASP.NET Web Forms, WinForms, Java, COBOL front-ends with SQL back-ends, and so on):

1. **Inventory the applications** that share data or business processes. Treat each as a Stage 1 unit.
2. **Adapt the Stage 1 prompt per app:** change the role line (for example, *"specializing in VB.NET WinForms and ADO.NET"*), the allowed paths, the technical discovery list (for example code-behind, `DataSet`s, `SqlCommand`, `Handles` clauses), the output folder, and the ID prefix.
3. **Build a small ground truth** with subject-matter experts (see Stage 0) and withhold it from Kiro, so you can run Stage 3 and know how far to trust the analysis.
4. **Keep Stage 2's two phases.** Consolidating from analyses first and then verifying against source is what prevents invented relationships.
5. **Change the target in Stage 4** to your chosen architecture, keeping the rules about traceability, parity, API compatibility, and the readiness gate.
6. **Keep Stage 5 incremental**, with build and test after every milestone, and require a validation report backed by executed tests.
7. **Keep humans at the gates.** Review and commit after every stage.

### Prompt-writing patterns worth reusing

| Pattern | Example from the prompts |
|---|---|
| Explicit scope and isolation | *"Analyze only... Do not analyze any other application."* |
| Evidence requirement | *"Every substantive business finding must contain a source reference."* |
| Honest verification labels | `static_verified` / `behavior_verified` / `inferred` |
| Anti-shortcut rules | *"Do not equate C# classes or UI screens directly with business capabilities."* |
| Fixed deliverables and stable IDs | `OD-CAP-001`, `CP-RULE-001`, `FA-WF-001` |
| No fabricated results | *"Do not claim tests passed without executing them."* |
| Plan before build | *"Produce the planning artifacts before generating implementation code."* |

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Kiro reads files outside the stage scope | The prompt alone was not enough | Start a new session; attach only the allowed `#Folder` contexts; add *"Do not open files under ..."* to the prompt |
| Kiro stops before producing all deliverables | Long task or context limit | Reply *"Continue and complete all remaining deliverables."* For Stage 5, use the resume message from Stage 5, step 6 |
| Findings claimed as `behavior_verified` without tests | The agent over-claimed | Ask Kiro to downgrade any finding not backed by a test run in the session |
| `Cannot open database "LegacyRetailDB"` | Database not provisioned or wrong connection | Run `./scripts/provision-db.ps1`; check `LEGACYRETAIL_CONNECTION` |
| OrderDesk will not build | Not on Windows | WPF requires Windows; the other projects build anywhere |
| Integration tests fail but unit tests pass | Database missing or stale | `./scripts/provision-db.ps1 -Reset` (disposable local DB only) |
| Port 5280 / 5101 / 5201 already in use | Another app instance is running | Stop the other process or change `Properties/launchSettings.json` |
| `score.py` errors on import | PyYAML missing | `pip install pyyaml`, or rely on the script's embedded fallback tables |
| Your Stage 3 score is much lower than the reference | Stage 1 missed findings, or Stage 2 merged them away | Read `stage-comparison.md` and `false-negatives.md`; rerun the weak Stage 1 session in a new Kiro session |
