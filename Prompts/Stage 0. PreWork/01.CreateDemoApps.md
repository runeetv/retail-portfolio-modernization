# Master Build Prompt: LegacyRetailPortfolio (.NET 10)

## Role and Objective

You are a Principal .NET Software Architect and Senior Full-Stack Engineer.

Build a realistic, working sample enterprise application portfolio named **LegacyRetailPortfolio**.

The portfolio will be used as a controlled benchmark for evaluating AI-powered application reverse engineering, business capability discovery, domain reconstruction, dependency analysis, and modernization planning.

The objective is NOT to build an ideal greenfield architecture. Instead, simulate an enterprise portfolio where applications have evolved independently, share some business capabilities, own other distinct domains, and interact with a common database.

All applications must be implemented using **.NET 10**.

The final solution must compile, run, contain meaningful business logic, and support demonstrable end-to-end workflows.

Do not simply scaffold empty controllers, services, pages, or repositories.

---

## 1. High-Level Architecture

Create three independently deployable applications:

**Application A: OrderDesk**
- .NET 10
- WPF desktop application
- Internal retail sales and order management
- C# and XAML
- EF Core 10 and SQL Server

**Application B: CustomerPortal**
- .NET 10
- ASP.NET Core MVC with Razor views
- Customer-facing self-service application
- EF Core 10 and SQL Server

**Application C: FulfillmentAPI**
- .NET 10
- ASP.NET Core Web API using controllers
- Swagger/OpenAPI documentation
- Warehouse and fulfillment operations
- EF Core 10 and SQL Server

All three applications access a single SQL Server database called `LegacyRetailDB`.

Each application must have its own independently defined domain models, application services, repositories/data access components, validations, and business workflows.

Do not create a shared business-logic library used by all three applications.

Sharing basic infrastructure utilities is acceptable, but business rules and entity models should primarily live within individual application projects.

## 2. Design Philosophy

This is a partially overlapping enterprise portfolio.

Follow these principles:

1. Each application must have a distinct primary business responsibility.
2. Some functionality should overlap between two or three applications.
3. Other functionality must belong exclusively to one application.
4. Some overlapping capabilities should be implemented differently.
5. Applications may use the same underlying database tables while maintaining different C# entity models.
6. Some business rules should be located in C# services, while others should be enforced by SQL stored procedures or constraints.
7. Data relationships and business processes should occasionally cross application boundaries.
8. The overall design should be believable as the result of independent development by multiple teams over several years.
9. Avoid deliberate syntax errors, broken builds, security vulnerabilities, or data corruption.
10. Functional behavior must remain deterministic and testable.

**Critical:** Do not interpret partial overlap as permission to duplicate every capability. Most application-specific functionality should be genuinely unique.

Aim for roughly:
- 50–60% application-specific capabilities.
- 20–30% partially overlapping capabilities.
- 15–20% broadly shared capabilities.

These are design targets, not strict mathematical quotas. Measure coverage using a capability catalog, not lines of code.

## 3. Application A — OrderDesk

### Business Purpose

OrderDesk is an internal desktop application used by sales representatives and customer service personnel.

### Core Features

Implement:

1. Search and view customers.
2. Update customer contact information.
3. Browse product catalog.
4. Create sales quotations.
5. Add quotation line items.
6. Apply manually approved discounts.
7. Convert approved quotations into orders.
8. Create staff-assisted orders.
9. View order details and status.
10. Cancel eligible orders.
11. Check inventory availability.
12. Initiate and approve customer returns.
13. Display assigned sales-agent tasks.

### Unique Domain Entities

- SalesQuote
- SalesQuoteLine
- DiscountApproval
- SalesAgent
- SalesAgentTask
- SalesCommission

### Business Rules

Implement meaningful rules, such as:

- Quotations expire after a configurable number of days.
- Discounts above a configurable threshold require approval.
- Only approved quotations may convert into orders.
- Sales-agent commissions depend on order value and discount level.
- Internal agents may override certain customer-facing cancellation restrictions with explicit authorization and an audit record.
- Orders cannot be created when mandatory customer information is missing.
- Quote conversion must be transactionally safe and prevent double conversion.

### Technical Requirements

Use WPF with MVVM-style separation.

Provide functional views for customers, products, quotations, orders, and discount approvals.

Use EF Core for most data access, but use at least one stored procedure for a business operation.

Keep OrderDesk's internal customer and order models separate from the models in the other applications.

## 4. Application B — CustomerPortal

### Business Purpose

CustomerPortal is a self-service shopping and customer-account web application.

### Core Features

Implement:

1. Customer sign-in using development-friendly local authentication.
2. View and update own profile.
3. Browse products.
4. Search products by name or category.
5. Add/remove products from shopping carts.
6. View and edit cart quantities.
7. Apply promotional coupon codes.
8. Place an order from a cart.
9. View own order history.
10. Request cancellation of eligible orders.
11. Create return requests.
12. View shipment tracking information.
13. Submit and view support tickets.
14. Maintain a wishlist.

### Unique Domain Entities

- CustomerAccount
- ShoppingCart
- ShoppingCartItem
- Wishlist
- WishlistItem
- SupportTicket
- SupportTicketMessage
- CustomerPreference
- CouponRedemption

### Business Rules

- Customers may access only their own account information, carts, tickets, and orders.
- Customer-initiated cancellation is allowed only for eligible order states.
- Coupon eligibility depends on coupon type, customer status, and cart total.
- Saved carts may contain products that are currently unavailable.
- Inventory availability must be rechecked before checkout.
- Returns are allowed only within the configured return window.
- Support tickets must have valid status transitions.
- Checkout must be idempotent to prevent accidental duplicate orders.

### Technical Requirements

Use ASP.NET Core MVC with Razor views.

Implement a simple but usable user interface with Bootstrap or comparable styling.

Use EF Core 10 with SQL Server.

Use strongly typed view models.

Use proper authorization and antiforgery protection.

Include a few intentional architectural differences from OrderDesk. For example, customer cancellation eligibility may be implemented in an application service while OrderDesk uses a SQL stored procedure.

Differences must be documented for benchmark purposes.

## 5. Application C — FulfillmentAPI

### Business Purpose

FulfillmentAPI supports warehouse execution, shipment processing, inventory allocation, and logistics integrations.

### Core Features

Implement REST APIs for:

1. Retrieving pending fulfillment orders.
2. Checking product availability.
3. Reserving or allocating inventory.
4. Creating picking lists.
5. Assigning warehouse bins.
6. Marking items as picked.
7. Creating shipment packages.
8. Updating shipment status.
9. Recording carrier events.
10. Retrieving shipment tracking.
11. Receiving returned merchandise.
12. Adjusting inventory based on returned stock.
13. Generating warehouse activity summaries.

### Unique Domain Entities

- Warehouse
- WarehouseBin
- PickList
- PickListItem
- InventoryAllocation
- ShipmentPackage
- CarrierEvent
- ReturnReceipt
- WarehouseAdjustment

### Business Rules

- Inventory cannot be allocated beyond available stock.
- Picking cannot begin before inventory allocation.
- Items must be picked before shipment packaging.
- A shipment cannot be marked dispatched without a package and carrier reference.
- Warehouse return receipt does not automatically imply financial refund approval.
- Certain order states must block fulfillment processing.
- Repeated shipment events must be handled idempotently.

### Technical Requirements

Use ASP.NET Core Web API controller-based endpoints.

Use EF Core 10 and SQL Server.

Provide OpenAPI documentation.

Use standard HTTP status codes, model validation, structured logging, and centralized error handling.

Implement at least two stored-procedure-based operations.

Use a development API key or another simple documented authentication mechanism.

Create sample HTTP requests or an API test collection.

## 6. Shared Database Design

Create a SQL Server database named `LegacyRetailDB`.

Use a mixture of shared tables and application-specific tables.

### Shared Tables

At minimum:

- Customers
- Products
- ProductCategories
- Orders
- OrderLines
- Inventory
- Returns
- ReturnLines

### OrderDesk-Owned Tables

- SalesQuotes
- SalesQuoteLines
- DiscountApprovals
- SalesAgents
- SalesAgentTasks
- SalesCommissions

### CustomerPortal-Owned Tables

- CustomerAccounts
- ShoppingCarts
- ShoppingCartItems
- Wishlists
- WishlistItems
- SupportTickets
- SupportTicketMessages
- CustomerPreferences
- Coupons
- CouponRedemptions

### FulfillmentAPI-Owned Tables

- Warehouses
- WarehouseBins
- InventoryAllocations
- PickLists
- PickListItems
- Shipments
- ShipmentPackages
- CarrierEvents
- ReturnReceipts
- WarehouseAdjustments

Add appropriate primary keys, foreign keys, unique constraints, checks, and indexes.

Create realistic cross-domain relationships.

For example:

- Orders can originate from OrderDesk or CustomerPortal.
- FulfillmentAPI processes eligible orders regardless of origin.
- CustomerPortal displays tracking data created by FulfillmentAPI.
- OrderDesk approves a return; FulfillmentAPI records receipt of the merchandise.
- A return created in CustomerPortal may subsequently be reviewed in OrderDesk.

Preserve actual referential integrity wherever practical.

### Important Database Requirements

- All applications must use the same physical SQL Server database.
- Use application-specific EF Core DbContexts with appropriately scoped entity mappings.
- Do not create a single universal DbContext shared by all three applications.
- Shared tables may have distinct C# entity representations.
- Establish a clear database migration ownership strategy.
- Provide a reproducible schema initialization process.
- Use SQL Server stored procedures for selected important operations.
- Include realistic indexes and constraints.

For reproducibility, use a dedicated database provisioning project that owns schema creation and migrations. Individual applications may query and update the shared schema but must not independently modify its structure at runtime.

## 7. Intentional Cross-Application Overlap

Create the following overlap scenarios.

### Scenario 1: Customer Management

OrderDesk allows staff to edit general customer contact information.

CustomerPortal allows customers to update a smaller subset of their own information.

FulfillmentAPI reads shipping-related information only.

Do not make all three applications implement full customer management.

### Scenario 2: Order Creation

OrderDesk creates staff-assisted orders, potentially from sales quotations.

CustomerPortal creates orders through shopping-cart checkout.

FulfillmentAPI does not create sales orders.

Order creation should share the final database structures while differing in workflow and validation.

### Scenario 3: Cancellation Rules

OrderDesk allows authorized staff cancellations with carefully controlled exceptions.

CustomerPortal provides more restrictive customer cancellation.

FulfillmentAPI rejects allocation or shipment processing for canceled orders.

Include at least one meaningful difference between the rule implementations.

### Scenario 4: Inventory

OrderDesk checks stock before accepting an order.

CustomerPortal displays availability and checks again at checkout.

FulfillmentAPI allocates stock for physical warehouse operations.

Do not make these identical capabilities.

### Scenario 5: Returns

CustomerPortal creates a return request.

OrderDesk reviews and approves or rejects the request.

FulfillmentAPI records physical receipt of returned goods.

A single business process therefore spans three applications, but each owns different capabilities.

### Scenario 6: Shipment Tracking

FulfillmentAPI owns shipment events.

CustomerPortal displays shipment events in a customer-friendly format.

OrderDesk may display shipment status for customer service purposes.

This is shared information with different application responsibilities, not three independent shipment-management implementations.

## 8. Intentional Architectural Imperfections

The portfolio should contain believable patterns for reverse-engineering agents to discover.

Include approximately:

- 3 duplicated business validation rules across applications.
- 2 semantically overlapping capabilities implemented using different names.
- 2 business rules enforced through SQL stored procedures.
- 2 cases where different C# domain models map to the same SQL table.
- 2 workflows spanning multiple applications.
- 1 meaningful inconsistency in terminology.
- 1 meaningful but bounded difference in cancellation eligibility logic.
- 1 complex SQL query that joins tables from multiple business domains.

Do not intentionally introduce exploitable vulnerabilities, missing authorization, silent data loss, or broken workflows.

Any conflicting rules must be implemented as deterministic, testable business behavior.

## 11. Required End-to-End Workflows

Implement and validate these workflows.

### Workflow A: Staff Order

Sales agent creates quotation → discount approval → quotation conversion → order creation → warehouse allocation → picking → shipment.

### Workflow B: Customer Checkout

Customer adds products to cart → applies coupon → checks out → order created → warehouse fulfillment → shipment tracking visible in portal.

### Workflow C: Customer Return

Customer requests return → OrderDesk approves return → warehouse records received items → inventory is adjusted → return reaches an appropriate final status.

### Workflow D: Cancellation

Customer requests cancellation → eligibility is evaluated → status changes → FulfillmentAPI prevents further allocation or shipment processing.

### Workflow E: Warehouse Fulfillment

Warehouse receives pending order → inventory allocation → picking → packaging → carrier dispatch → tracking event updates.

All workflows must use persisted SQL Server data, not mock or in-memory repositories.


## 15. Implementation Strategy

Do not stop after generating an architectural plan.

Implement the portfolio incrementally:

**Phase 1:** Repository structure, projects, SQL schema, database provisioning, and seed data.

**Phase 2:** OrderDesk business logic and WPF functionality.

**Phase 3:** CustomerPortal business logic and MVC functionality.

**Phase 4:** FulfillmentAPI and warehouse workflows.

**Phase 5:** Cross-application workflows and integration testing.

**Phase 6:** Ground-truth benchmark generation and documentation.

At each phase:
- Compile the relevant projects.
- Run appropriate tests.
- Correct compilation and functional failures.
- Maintain a short implementation-progress file.
- Record any deviations from the specified architecture.

If a tool, dependency, or environment is missing, record the blocker explicitly rather than claiming successful execution.

## 16. Acceptance Criteria

The project is complete only when:

- All projects compile on their documented target environments.
- All three applications use .NET 10.
- SQL Server is used for persisted business data.
- Applications contain real business logic.
- Application-specific entities and capabilities genuinely exist.
- The intended partial overlap is demonstrated.
- Shared business entities are represented through independently maintained application models.
- End-to-end workflows are functional.
- Tests pass on a correctly provisioned environment.
- Ground-truth documentation corresponds to the implemented code.
- A separate reverse-engineering agent can analyze the portfolio without needing ground-truth files.

Do not simplify the project into three CRUD applications with identical customer and order screens.

The ultimate success criterion is whether the portfolio provides a realistic benchmark for **AI-assisted enterprise application portfolio discovery, semantic reconstruction, capability rationalization, and modernization planning**.

Start with the architecture and implementation plan, then proceed to writing code.
