# LegacyRetailPortfolio — Consolidation Requirements and Target Design Preparation

## Role

You are a Principal Enterprise Modernization Architect specializing in .NET application consolidation, domain-driven design, business capability mapping, and backward-compatible API modernization.

## Objective

We have three existing .NET 10 applications:

- OrderDesk
- CustomerPortal
- FulfillmentAPI

Their business capabilities, entities, business rules, workflows, and cross-application dependencies have already been reconstructed through AI-assisted reverse engineering.

The target is predetermined:

**Consolidate all existing business functionality into one ASP.NET Core web application with an API layer that preserves supported backward compatibility contracts.**

Your task is to translate the verified reverse-engineering findings into a comprehensive, evidence-backed consolidation specification.

Do not implement the new application yet.

## Inputs

Use:

- Verified Stage 1 application analyses
- Verified Stage 2 portfolio architecture and capability catalogs
- Stage 3 evaluation results
- Source code and SQL DDL for targeted verification

Ground-truth benchmark artifacts may be used by a separate reviewer for validation, but do not use them to conceal gaps in the original reverse-engineering findings.

## Task 1 — Consolidated Functional Requirements

Create a single unified requirements catalog.

For every existing capability, identify:

- Source application
- Original capability ID
- Business purpose
- Actors and roles
- Business rules
- Inputs and outputs
- Relevant entities
- Workflows
- Target web feature
- Target application module
- Functional parity requirements
- Supporting evidence

Every existing capability must receive an explicit disposition.

No functionality may be silently discarded.

## Task 2 — Overlap Reconciliation

Identify capabilities implemented by more than one application.

For each overlap:

- Describe common behavior.
- Describe application-specific behavior.
- Identify duplicated implementation logic.
- Identify business-rule differences.
- Recommend which logic can be unified.
- Identify policies that must remain context-specific.
- Highlight decisions requiring business stakeholder approval.

Do not treat all differences as defects.

## Task 3 — Unified Domain Design

Propose logical domain modules and boundaries.

Evaluate existing entities, entity relationships, and physical database tables.

Determine:

- Canonical business concepts
- Domain-specific models
- Entity ownership
- Shared data dependencies
- Required domain interfaces
- Transaction boundaries
- Database migration considerations

Do not automatically merge all entity classes representing the same database table.

Preserve distinctions required by business context.

## Task 4 — Unified User Experience Requirements

Map existing application functionality into web-based user journeys.

Identify:

- Internal staff operations
- Customer self-service
- Warehouse operations
- Role-based navigation
- Permissions
- Shared workflows
- Application-specific views
- Desktop-to-web migration considerations

Define functional screens and their associated business operations.

Avoid designing visual mockups at this stage.

## Task 5 — Backward Compatibility Analysis

Inventory existing API contracts and consumers.

For each existing endpoint record:

- Route and HTTP method
- Request and response models
- Authentication requirements
- Business behavior
- Status codes
- Error formats
- Idempotency behavior
- Dependencies
- Proposed compatibility strategy
- Required contract tests

Distinguish demonstrated external contracts from internal-only implementation methods.

Do not invent external consumers.

Where compatibility obligations are unknown, record them as questions rather than assumptions.

## Task 6 — Data Consolidation Analysis

Assess the existing SQL Server database.

Identify:

- Tables retained
- Tables potentially merged
- Schema changes required
- Migration risks
- Data ownership
- Referential integrity constraints
- Stored procedure dependencies
- Data access changes
- Historical data preservation requirements

Prefer minimizing unnecessary database changes during the initial consolidation unless a change has a clear benefit.

## Task 7 — Functional Parity Matrix

Create an exhaustive mapping between current functionality and target requirements.

For every source capability identify:

- Target feature/module
- Required behavior
- Acceptance criteria
- Existing automated tests
- New parity tests needed
- Known ambiguities
- Migration risk
- Verification status

Identify any capabilities missing from the initial consolidated design.

## Task 8 — Recommended Implementation Architecture

Recommend a pragmatic ASP.NET Core .NET 10 architecture.

Prefer a modular monolith unless evidence justifies additional deployable services.

Describe:

- Web UI layer
- API and compatibility adapters
- Application services
- Domain modules
- Persistence architecture
- Authentication/authorization
- Integration patterns
- Module boundaries
- Testing strategy

Document tradeoffs and alternative options.

Do not prematurely introduce microservices.

Generate:

```text
consolidation-planning/
├── unified-capability-catalog.yaml
├── capability-reconciliation.yaml
├── consolidated-domain-model.md
├── module-ownership-matrix.yaml
├── unified-web-requirements.md
├── api-compatibility-inventory.yaml
├── data-consolidation-assessment.md
├── functional-parity-matrix.yaml
├── architecture-options.md
├── consolidation-decisions.md
└── consolidation-readiness-report.md
```

Every recommendation must reference its source discovery evidence.

Explicitly distinguish:

- Verified existing behavior
- Proposed target behavior
- Business decisions required
- Technical assumptions
- Unresolved gaps

## Completion Criteria

The consolidation specification is complete when:

1. Every discovered existing capability has a target disposition.
2. Unique functionality from all three applications is preserved.
3. Partial overlaps are reconciled without erasing legitimate differences.
4. All significant business rules are represented.
5. Cross-application workflows have target equivalents.
6. Existing APIs have a documented compatibility strategy.
7. Shared data dependencies are understood.
8. Functional parity is demonstrable through planned tests.
9. Unknowns and business decisions are explicitly documented.
10. The proposed architecture is implementable without requiring further reverse engineering for ordinary development tasks.

Produce the planning artifacts before generating implementation code.
