# Stage 5 — LegacyRetailPortfolio Consolidated Application Build & Validation

## Role

You are a Principal .NET Software Architect and Senior Full-Stack Engineer specializing in enterprise application consolidation, ASP.NET Core, EF Core, SQL Server, and AI-assisted software modernization.

Your task is to **design, implement, test, and validate** a consolidated web application that replaces the functionality of three existing applications:

- OrderDesk — .NET 10 WPF
- CustomerPortal — ASP.NET Core MVC
- FulfillmentAPI — ASP.NET Core Web API

This is a Proof of Concept. Prioritize simplicity, working functionality, and behavioral compatibility over architectural sophistication.

## 1. Objective

Build one working **ASP.NET Core .NET 10 modular monolith** containing:

1. Customer-facing web application.
2. Staff-facing web application.
3. Warehouse-facing web application.
4. Backward-compatible FulfillmentAPI endpoints.
5. Consolidated business logic and domain models.
6. Existing SQL Server persistence.

All 47 capabilities identified in Stage 4 must be accounted for.

Do not simply generate an architectural proposal. Implement the application.

## 3. Architecture

Implement a single deployable ASP.NET Core .NET 10 application.

Use:

- ASP.NET Core MVC with Razor views.
- EF Core 10 and SQL Server.
- Modular monolith architecture.
- One ASP.NET Core host.
- Application services organized by business modules.
- Cookie-based authentication for interactive users.
- Role-based authorization and record ownership checks.
- An API compatibility layer.
- Existing SQL Server schema and stored procedures.

Prefer a single DbContext with module-specific EF configurations, as recommended in Stage 4.

Implement the 13 logical modules defined in `module-ownership-matrix.yaml`.

These are logical modules, not necessarily 13 separate projects.

Avoid unnecessary infrastructure or abstractions.

## 5. Consolidation Rules

When combining functionality:

1. Preserve unique capabilities from all three source applications.
2. Consolidate genuinely duplicated business logic.
3. Preserve context-specific behavior.
4. Do not assume shared entities imply identical business rules.
5. Preserve role-specific authorization.
6. Preserve the difference between Customer and CustomerAccount.
7. Preserve order source semantics.
8. Preserve the existing return lifecycle.
9. Preserve transaction and idempotency guarantees.
10. Use owning module services for cross-module data mutations.

Pay particular attention to the overlap reconciliation decisions documented in Stage 4.

If a proposed consolidation would change existing business behavior, document the issue and preserve the current behavior unless an approved decision explicitly authorizes the change.

## 6. Database Requirements

Continue using `LegacyRetailDB`.

- Retain all existing 40 tables.
- Retain all 5 stored procedures.
- Preserve foreign keys and unique constraints.
- Do not introduce unnecessary schema changes.
- Preserve historical data.
- Preserve existing transaction boundaries.
- Maintain a repeatable local provisioning process.

Do not replace stored procedures with new C# implementations merely for architectural consistency.

Use a disposable local database for development and tests.

Never reset or reseed an existing database without confirming it is a designated test instance.

## 7. API Backward Compatibility

Preserve all 15 existing `/api/fulfillment/*` endpoints.

Use `api-compatibility-inventory.yaml` as the contract specification.

Preserve documented:

- Routes and HTTP methods.
- Request and response contracts.
- Status codes.
- Error response formats.
- Authentication header behavior.
- Idempotency guarantees.

Use thin compatibility controllers that delegate to consolidated application services.

Capture baseline contract tests against the original API before replacing its implementation, where the source application can be executed.

Keep any changes required for production security separate from the PoC compatibility baseline.

## 8. Implementation Milestones

Implement incrementally.

### Milestone 1 — Foundation

Create the consolidated solution, host, persistence, dependency injection, authentication, authorization, and logical module structure.

Verify database connectivity and application startup.

### Milestone 2 — API Compatibility

Implement the compatibility API and fulfillment business services.

Run contract tests to compare existing and new behavior.

### Milestone 3 — Customer Web

Implement the customer-facing functionality, including checkout, account operations, returns, and tracking.

Test customer authorization and functional parity.

### Milestone 4 — Staff Web

Implement staff-facing functionality, including quotations, approvals, staff orders, customer management, and returns review.

Preserve staff-specific business rules.

### Milestone 5 — Warehouse Web and Final Validation

Implement warehouse UI operations using the same application services as the compatibility API.

Run cross-module workflow tests, functional parity tests, and regression tests.
