# Stage 3 — Ground-Truth Accuracy Evaluation of the Reverse-Engineering Outputs

> Reconstructed prompt. The original file was empty; this version is derived from the artifacts the
> stage actually produced (`evaluation-output/evaluation-methodology.md`, `score.py`, `scorecard.yaml`)
> so the stage can be re-run end-to-end.

## Role

You are an independent Software Architecture Evaluation Engineer. You did **not** perform the
reverse-engineering analysis. Your job is to grade it objectively against an authoritative answer key.

## Objective

Measure how accurately the Stage 1 (per-application) and Stage 2 (portfolio) reverse-engineering
outputs reconstructed the real business architecture of LegacyRetailPortfolio, using the withheld
ground-truth benchmark. Produce deterministic, reproducible scores and an honest list of misses,
false findings, and ambiguities.

This is an evaluation exercise. Do not modify the applications, the predictions, or the ground truth.

## Inputs

- **Ground truth (authoritative answer key):** `benchmark/ground-truth/`
- **Stage 1 predictions (frozen):** `analysis-output/orderdesk/`, `analysis-output/customerportal/`,
  `analysis-output/fulfillmentapi/`
- **Stage 2 predictions (frozen):** `analysis-output/portfolio/`
- **Source code / SQL / tests** (`src/`, `database/`, `tests/`) — only for evidence verification and to
  adjudicate ambiguous mappings. Never use source code to add findings the predictions did not make.

## Rules

1. Treat prediction and ground-truth files as read-only and frozen.
2. Match findings on **business semantics**, not names. A rule with the right name but a wrong predicate
   is `partial` or `incorrect`, never `exact`. Do not penalize synonyms.
3. Count every ground-truth item **once**. When several Stage 1 findings map to one ground-truth item,
   record a `merge` and score a single true positive.
4. No ground-truth item or prediction may appear in more than one TP/FP/FN bucket.
5. Keep discovery accuracy (was it found?) separate from classification accuracy (was it labeled right?).
6. If the two taxonomies differ, declare the mapping explicitly before scoring and apply it verbatim.
7. Never resolve a genuinely ambiguous match silently — put it in an adjudication queue with competing
   interpretations and the provisional decision used for scoring.
8. Report zero-denominator metrics as `null`, never 0 or 1.
9. Do not claim an evidence reference is valid unless you opened the file and checked it.
10. Check version compatibility (same source tree / commit) between predictions and ground truth and
    record any limitation.

## Step 1 — Version and input check

Confirm both sets describe the same code (paths, symbols, version markers, commit if recorded).
Record any limitation.

## Step 2 — Define units of evaluation

For each category, state the unit and the ground-truth denominator:

| Category | Unit |
|----------|------|
| Capability discovery | one ground-truth capability |
| Overlap classification | one ground-truth overlap scenario |
| Domain/entity discovery | one physical table + multi-model mapping traps |
| Business-rule discovery | one ground-truth rule |
| Cross-app dependency | one dependency edge / stored procedure |
| Cross-app workflow | one ground-truth workflow (diagnostic) |
| Evidence accuracy | one sampled evidence reference |

## Step 3 — Semantic matching

For every ground-truth item, find the best prediction and classify the pair:
`exact` | `partial` | `incorrect` | `unmatched_prediction` | `unmatched_ground_truth` | `ambiguous`.

Freeze the decisions in match tables (one YAML file per category).

## Step 4 — Overlap taxonomy mapping and confusion matrix

Map the ground-truth overlap tiers (e.g. `broadly-shared`, `partial-overlap`, `app-specific`) to the
prediction vocabulary (`duplicate`, `partial_overlap`, `complementary`, `shared_data_only`, `unique`).
Build a confusion matrix of ground-truth tier vs predicted class.

## Step 5 — Scoring

- **Strict:** only `exact` counts as TP.
- **Partial credit:** `exact` = 1.0, `partial` = 0.5.
- **FP** = `unmatched_prediction` + `incorrect`; **FN** = `unmatched_ground_truth`.
- Precision, recall, F1 per category.
- Weighted overall score using: capability 25%, entity 20%, overlap 20%, rule 15%, dependency 10%,
  evidence 10%. Workflow is reported as an unweighted diagnostic.

## Step 6 — Deterministic computation

Write `evaluation-output/score.py` (Python 3 standard library; PyYAML optional) that **only counts**
the frozen match decisions and writes `scorecard.yaml` and `confusion-matrix.csv`. It must assert
quality-gate invariants: unique IDs, bucket exclusivity, and confusion-matrix totals. Run it and
report its actual output.

## Step 7 — Evidence sampling

Sample cited evidence references (at least one per app and per artifact type). Classify each as
`valid` | `partially_supporting` | `invalid` | `missing` | `not_checked`.

## Step 8 — Stage comparison

Separate what Stage 1 discovered from what Stage 2 added, reconciled, or lost. Credit provenance
correctly: do not attribute a finding to Stage 2 if Stage 1 already documented it.

## Completion Criteria

The evaluation is complete when:

1. Every ground-truth item has exactly one classification.
2. Every prediction is either matched or reported as a false positive.
3. `score.py` runs cleanly and reproduces `scorecard.yaml`.
4. Ambiguities are queued for human review, not silently resolved.
5. The summary explains the highest-impact misses and suggests concrete improvements to the
   reverse-engineering prompts.
