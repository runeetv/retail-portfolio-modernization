## Additional Requirements — Stage 3-Informed Consolidation

The preceding reverse-engineering evaluation reported:

- Weighted overall accuracy: 95.5%
- Discovery completeness: 100% reported recall
- Capability discovery score: 98%
- Domain/entity score: 100%
- Business-rule score: 100%
- Cross-application dependency score: 100%
- Overlap classification score: 82.5%
- Evidence accuracy: 95.5%

These scores are contextual evaluation results, not proof that every finding is correct.

### A. Resolve Uncertain Overlap Classifications

Before consolidating any functionality:

1. Review the Stage 3 overlap evaluation and confusion matrix.
2. Identify incorrectly classified, ambiguous, or partially supported relationships.
3. Revalidate affected relationships against source code and SQL.
4. Distinguish actual duplication from partial overlap, complementary responsibilities, and shared data access.
5. Mark unresolved cases as requiring business review.

Do not consolidate functionality solely because an AI analysis classified it as overlapping.

### B. Require Complete Functional Traceability

Every source capability must map to:

- Source application and capability ID
- Source implementation evidence
- Target functional requirement ID
- Target web feature or API operation
- Target domain module
- Preserved business rules
- Required user roles
- Functional parity acceptance criteria
- Planned regression tests

Report all unmapped capabilities.

Do not silently remove features, including application-specific functionality.

### C. Preserve Context-Specific Business Policies

When multiple applications implement related operations:

- Identify common business invariants.
- Identify actor-specific rules and permissions.
- Identify differences that require stakeholder decisions.
- Recommend consolidation of common logic only when behavior is genuinely equivalent.
- Preserve legitimate variations as explicit policies.

Do not treat every difference as a defect.

### D. Define API Backward Compatibility

For each existing externally consumed API:

- Preserve or explicitly disposition routes and HTTP methods.
- Capture request and response schemas.
- Capture authentication and authorization behavior.
- Preserve required status codes and error contracts.
- Identify idempotency guarantees.
- Create contract tests that verify compatibility.

Record unknown external consumers and undocumented contracts as open risks.

### E. Introduce a Consolidation Readiness Gate

Do not mark consolidation planning complete until:

1. Every discovered capability is mapped or explicitly dispositioned.
2. All high-impact overlap ambiguities are resolved or escalated.
3. Significant business rules have target implementations or documented decisions.
4. Cross-application workflows have defined target equivalents.
5. Existing supported API contracts have a compatibility strategy.
6. Functional parity acceptance criteria and test plans exist.
7. Target domain ownership and data access responsibilities are defined.
8. Unresolved assumptions and migration risks are documented.

Produce an additional `consolidation-readiness-checklist.md` identifying passed and failed readiness criteria.

Do not start implementing the new application until the planning outputs have been reviewed and approved.
