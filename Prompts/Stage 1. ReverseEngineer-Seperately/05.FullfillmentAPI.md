# Stage 1 — Independent Application Reverse Engineering: FulfillmentAPI

## Role

You are a Principal Software Reverse Engineering Architect specializing in .NET Web APIs, enterprise transaction processing, database-centric systems, and business workflow reconstruction.

Independently analyze **FulfillmentAPI**, a .NET 10 application within LegacyRetailPortfolio.

Your objective is to reconstruct the actual business capabilities, domain model, business rules, state transitions, and dependencies implemented by this application.

Do not redesign or modernize the application.

## 1. Scope and Isolation

You may inspect only:

- FulfillmentAPI source projects under `src/FulfillmentAPI/`
- Relevant shared infrastructure required by FulfillmentAPI
- SQL Server DDL and stored procedures used by FulfillmentAPI
- FulfillmentAPI-specific tests
- Required technical configuration

Do not access other applications, portfolio-level architecture documents, ground-truth files, or benchmark answer keys.

If the application processes records originating outside its boundary, describe the dependency without inferring details of the producer.

Do not compare this application with other applications.

## 2. Analysis Principles

1. Identify business capabilities rather than merely cataloging API endpoints.
2. Trace requests through controllers, application services, domain logic, and persistence.
3. Treat stored procedures and database constraints as sources of business behavior.
4. Distinguish business entities from transport DTOs.
5. Reconstruct state transitions and business process ordering.
6. Identify operations that mutate shared business records.
7. Differentiate ownership from read-only access.
8. Identify transactional boundaries, consistency requirements, and idempotency protections.
9. Ground all findings in verifiable implementation evidence.
10. Explicitly document uncertainty.

## 3. Technical Discovery

Inspect:

- API startup and dependency injection
- Controllers and endpoint routes
- Request/response models
- Authentication and authorization
- Application services
- Domain entities
- EF Core DbContext and mappings
- Raw SQL and stored procedure execution
- Transactions and concurrency controls
- Error handling
- API documentation
- Relevant tests

For each API endpoint, trace its underlying business effect.

Classify endpoints by business domain and operation.

## 4. Business Capability Discovery

Identify the complete set of meaningful business capabilities.

For each capability provide:

- Analysis-generated ID
- Business-oriented name
- Description
- Business actor or calling system
- API entry point
- Preconditions
- Business decisions
- Resulting state changes
- Domain objects involved
- Database reads and writes
- Related rules
- Source-code evidence
- Confidence and verification status

Do not automatically create one capability per endpoint.

Group related operations under the appropriate business capability when they contribute to a common business objective.

## 5. Domain Entity Reconstruction

Identify domain entities and business concepts.

For every significant entity record:

- Entity ID
- Business name and responsibility
- Key attributes
- Relationships
- Lifecycle
- Source class and namespace
- Database table mapping
- Read/write/ownership evidence
- Associated capability IDs
- Confidence level

Distinguish operational business entities from integration DTOs and reporting projections.

Identify which entities are created or primarily maintained by the application and which are consumed from external data sources.

## 6. Business Rule Extraction

Discover rules governing operational decisions.

Pay particular attention to:

- Resource availability
- Allocation constraints
- Preconditions for operations
- Sequencing of business steps
- Status transitions
- Invalid or duplicate operations
- Transactional integrity
- Concurrency behavior
- Reversal and exception handling
- Business events and external references

For each rule record:

- Rule ID
- Name
- Business description
- Preconditions
- Decision or predicate
- Resulting action
- Related entity and capability IDs
- Enforcement layer
- Exact code or SQL evidence
- Relevant test evidence
- Confidence
- Verification status

Inspect the actual bodies of relevant SQL stored procedures, not just their names or call sites.

## 7. State Machine Reconstruction

Identify entities with meaningful business state transitions.

For each:

1. Enumerate observed states.
2. Identify allowed transitions.
3. Identify the triggering operation.
4. Identify guards or preconditions.
5. Identify state-changing database operations.
6. Identify invalid transitions.
7. Record source evidence.

Generate Mermaid state diagrams where appropriate.

Do not infer unsupported states or transitions from naming conventions alone.

## 8. Workflow Reconstruction

Reconstruct significant end-to-end workflows implemented by the API.

For every workflow identify:

- Business objective
- Initiating actor or caller
- Entry points
- Steps and ordering requirements
- Domain entities
- State transitions
- Database operations
- Stored procedures
- Transaction boundaries
- Error handling and alternative paths
- External data dependencies
- Evidence

Use sequence diagrams or flowcharts where helpful.

Distinguish operations performed within FulfillmentAPI from activities performed by unknown external producers or consumers.

## 9. Database Dependency Analysis

Produce a mapping of SQL objects accessed by the application.

For each SQL object include:

- SQL object name
- Access type (read/write/execute)
- Corresponding C# entity or service
- Business purpose
- Whether the application creates or modifies the data
- Relevant source reference
- Relevant stored procedure calls

Identify joins spanning distinct business areas.

Do not infer functional duplication based only on shared table access.

## 10. Evidence and Confidence

Every substantive finding must be supported by an implementation reference.

Provide repository-relative paths, symbols, and line ranges where available.

Use these confidence values:

- `high`
- `medium`
- `low`

Use these verification values:

- `static_verified`
- `behavior_verified`
- `inferred`

Do not report behavioral verification unless a test or actual execution demonstrates it.

Record unresolved assumptions separately.

## 11. Deliverables

Generate:

```text
analysis-output/fulfillmentapi/
├── application-profile.md
├── capabilities.yaml
├── entities.yaml
├── business-rules.yaml
├── workflows.yaml
├── dependencies.yaml
├── evidence-index.yaml
├── state-machines.md
├── analysis-gaps.md
└── summary.md
```

Use stable IDs:

- `FA-CAP-001`
- `FA-ENT-001`
- `FA-RULE-001`
- `FA-WF-001`

Ensure YAML is syntactically valid and references are consistent.

## 12. Execution Order

1. Inspect the permitted project structure.
2. Inventory controllers and API endpoints.
3. Trace endpoint implementations into application and domain services.
4. Identify entities and database mappings.
5. Examine relevant stored procedures and transactions.
6. Reconstruct business rules and state machines.
7. Reconstruct business workflows.
8. Build the capability catalog.
9. Validate source references and test evidence.
10. Generate the deliverables and report gaps.

Perform read-only analysis. Execute tests only where a safe test environment is available.

## 13. Completion Criteria

The analysis must enable another engineer to understand:

- What business functions the API performs
- Which operational domains it supports
- Its business entities and their lifecycles
- The rules governing its operations
- The state transitions it enforces
- Its database dependencies
- External business information it consumes
- Implementation evidence supporting each conclusion

Do not produce modernization recommendations.

Do not create a cross-application overlap analysis.

Do not access other application implementations.

Begin the analysis.
