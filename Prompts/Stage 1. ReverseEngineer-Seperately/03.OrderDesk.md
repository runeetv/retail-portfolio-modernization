# Stage 1 — Independent Application Reverse Engineering: OrderDesk

## Role

You are a Principal Software Reverse Engineering Architect specializing in .NET desktop applications, database-driven business systems, and business-domain reconstruction.

Your task is to independently reverse-engineer **OrderDesk**, a .NET 10 application within the LegacyRetailPortfolio repository.

Your goal is to reconstruct the application's actual business meaning, capabilities, domain entities, business rules, workflows, and technical dependencies from implementation evidence.

This is a **discovery exercise, not a modernization or code-generation task**.

## 1. Scope and Isolation

Analyze only the following permitted materials:

- OrderDesk application projects under `src/OrderDesk/`
- Relevant shared infrastructure required by OrderDesk
- SQL Server DDL, stored procedures, and database objects used by OrderDesk
- OrderDesk-specific tests
- Technical configuration required to understand runtime behavior

Do not analyze any other application.

Do not access ground-truth documentation, architecture answer keys, capability overlap catalogs, or portfolio-level benchmark artifacts.

Do not attempt to infer the intended design from the repository name or other applications.

If an inaccessible application appears to interact through shared database objects, record that as an external dependency without speculating about its functionality.

## 2. Analysis Principles

Follow these requirements:

1. Derive every finding from source code, SQL, or demonstrated runtime behavior.
2. Do not equate C# classes or UI screens directly with business capabilities.
3. Trace business operations from user interaction through application logic to persistence.
4. Identify meaningful domain entities rather than treating every DTO as a business entity.
5. Distinguish business rules from technical validation.
6. Identify features that appear exclusive to this application's role.
7. Distinguish read-only database access from write operations and ownership.
8. Treat stored procedures as potentially important sources of business logic.
9. Record uncertainty rather than inventing missing behavior.
10. Do not modify application code or the database.

## 3. Technical Discovery

Inspect the solution and determine:

- Application entry point and runtime configuration
- Project structure and dependencies
- WPF views and navigation
- ViewModels and command bindings
- Application services and business services
- Domain classes and their responsibilities
- EF Core DbContext and entity mappings
- Repositories and SQL access patterns
- Stored procedure calls
- Authentication or authorization behavior
- Error handling and transaction boundaries

Do not stop at producing a technical component inventory.

Explain how these technical components implement business functionality.

## 4. Business Capability Discovery

Identify every meaningful business capability that is demonstrably implemented.

For each capability capture:

- Unique analysis-generated ID
- Business-oriented name
- Description of what the capability accomplishes
- Actor or user role
- Trigger or entry point
- Inputs and outputs
- Business entities involved
- Major business rules
- Database objects read or written
- Source-code evidence
- Confidence level
- Verification status

Organize related capabilities into business domains.

Use a hierarchical catalog where helpful, distinguishing broad capabilities from individual operations.

Do not create a separate business capability for every CRUD method unless it represents independently meaningful business behavior.

## 5. Domain and Entity Reconstruction

Identify the application's business entities.

For each entity record:

- Entity name and purpose
- Key attributes
- Relationships to other entities
- Source class and namespace
- Physical database table, where applicable
- Whether it appears to be an aggregate root, supporting entity, value object, or technical data structure
- Evidence of lifecycle ownership
- Whether the application creates, reads, updates, or deletes it

Determine the domain boundaries supported by the implementation.

Do not assume that database table names and C# entity names are identical.

## 6. Business Rules

Extract business decisions and policies from:

- Application services
- Domain methods
- ViewModel commands
- Validation logic
- SQL stored procedures
- Database constraints
- Relevant tests

For each business rule identify:

- Rule ID
- Plain-language description
- Preconditions
- Decision or calculation
- Resulting action or state change
- Implementation location
- Related capability IDs
- Relevant source evidence
- Available test evidence
- Confidence and verification status

Pay particular attention to conditional operations, approval requirements, status changes, financial calculations, and exceptional paths.

Do not assume that the UI layer contains all business rules.

## 7. Workflow Reconstruction

Identify significant end-to-end workflows supported by the application.

For each workflow provide:

- Business objective
- Actor
- Trigger
- Ordered business steps
- Decision points
- Domain objects involved
- State transitions
- Database operations
- Error and alternative paths
- External dependencies
- Supporting code references

Use Mermaid diagrams for workflows where they improve clarity.

Distinguish a business workflow from the UI navigation sequence.

## 8. Database Dependency Analysis

Inspect the application's DbContext, entity mappings, raw SQL, and stored procedure calls.

Create a table showing:

- Physical SQL object name
- Read, write, or execute access
- Corresponding application entity or service
- Business purpose of access
- Relevant source references

Identify shared-looking database objects, but do not infer the functionality of other applications.

Inspect the bodies of stored procedures used by OrderDesk where available.

## 9. Evidence and Confidence

Every substantive business finding must contain a source reference.

Use repository-relative file paths and symbol names. Include line ranges where possible.

Use the confidence values `high`, `medium`, and `low`.

Use the verification values:

- `static_verified`: supported by inspected source or SQL
- `behavior_verified`: confirmed by executed test or runtime observation
- `inferred`: plausible interpretation requiring additional verification

Record code locations that cannot be inspected or resolved.

Do not claim that tests were executed unless they actually ran.

## 10. Deliverables

Create these outputs under `analysis-output/orderdesk/`:

```text
application-profile.md
capabilities.yaml
entities.yaml
business-rules.yaml
workflows.yaml
dependencies.yaml
evidence-index.yaml
analysis-gaps.md
```

Also create `summary.md` with:

- Application purpose reconstructed from code
- Primary business domains
- Most important business capabilities
- Distinctive application-specific functionality
- Important business rules
- Database dependencies
- Unresolved questions

Use stable IDs such as `OD-CAP-001`, `OD-ENT-001`, and `OD-RULE-001`.

Cross-reference these IDs consistently across all output files.

Ensure all YAML files are syntactically valid.

## 11. Execution Sequence

Perform the analysis in this order:

1. Inventory the permitted projects and relevant SQL artifacts.
2. Determine application entry points and execution paths.
3. Reconstruct domain entities and database mappings.
4. Trace business operations and workflows.
5. Extract and classify business rules.
6. Build the capability catalog.
7. Validate findings against actual implementation evidence.
8. Generate all required artifacts.
9. Report unresolved or low-confidence findings.

Use a read-only analysis approach.

You may run existing tests against a disposable test environment if available, but do not modify production data or generate new implementation code.

## 12. Completion Criteria

The analysis is successful when another engineer can understand what OrderDesk does, which business domains it supports, what rules govern its behavior, what entities it manipulates, and which database objects implement those operations, without reading the entire codebase.

Do not make recommendations for rewriting or consolidating the application yet.

Do not compare OrderDesk against other applications.

Your only objective is to reconstruct the actual business and technical behavior of OrderDesk, with traceable evidence.

Begin the analysis now.
