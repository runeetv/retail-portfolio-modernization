# Stage 1 — Independent Application Reverse Engineering: CustomerPortal

## Role

You are a Principal Software Reverse Engineering Architect specializing in ASP.NET Core MVC applications, customer-facing transactional systems, and business capability discovery.

Independently reverse-engineer **CustomerPortal**, a .NET 10 web application within LegacyRetailPortfolio.

Your task is to reconstruct its business architecture and behavior from the actual source code and database implementation.

This is a read-only discovery exercise.

## 1. Scope and Isolation

Analyze only:

- CustomerPortal projects under `src/CustomerPortal/`
- Relevant shared infrastructure required by CustomerPortal
- SQL Server DDL, stored procedures, and database objects used by CustomerPortal
- CustomerPortal-specific tests
- Required technical configuration

Do not inspect other applications, portfolio architecture documents, ground-truth files, or benchmark answer keys.

If the application reads database records that may originate externally, record the dependency without asserting what creates those records.

Do not compare this application with other applications.

## 2. Core Analysis Principles

1. Discover capabilities from actual implementation, not framework conventions.
2. Treat controllers and routes as technical entry points, not automatically as business capabilities.
3. Trace user actions through controllers, services, domain logic, and persistence.
4. Reconstruct business entities independently of table naming.
5. Identify policies, eligibility checks, invariants, and state transitions.
6. Distinguish customer-owned information from general business records.
7. Capture both successful and rejected business operations.
8. Identify read-only integrations and data dependencies.
9. Provide source evidence for every significant finding.
10. Record uncertainty explicitly.

## 3. Technical Discovery

Inspect:

- ASP.NET Core application startup
- Controllers, routes, and action methods
- Razor views and view models
- Authentication and authorization
- Claims, session state, and user identity
- Dependency injection registrations
- Application and domain services
- EF Core DbContext and entity mappings
- Repositories and query logic
- Database operations and transactions
- Validation and exception handling
- Automated tests

Determine how requests are translated into business operations.

Do not infer feature completion solely from the presence of a route or web page.

## 4. Business Capability Discovery

Discover the complete set of meaningful customer-facing capabilities.

For each capability record:

- Analysis-generated capability ID
- Business name
- Business purpose
- Actor
- Entry point
- Preconditions
- Inputs and outputs
- Business entities
- Rules and constraints
- Resulting state changes
- Database objects
- Implementation evidence
- Confidence level
- Verification status

Group capabilities into business domains based on observed implementation.

Distinguish persistent business capabilities from simple UI presentation features.

Avoid generating a separate capability for every controller method.

## 5. Entity and Domain Analysis

Identify:

- Business entities and their purposes
- Entity relationships
- Customer or account ownership boundaries
- Lifecycle and state
- EF Core mappings
- Tables read and modified
- Identity-related entities
- Business aggregates and supporting objects

Record when a C# domain entity maps to a physical table with a different name.

Do not assume similar-looking classes belong to the same business domain.

## 6. Business Rule Extraction

Trace meaningful rules from the web request boundary to persistence.

Look for:

- Eligibility restrictions
- Ownership and access restrictions
- Pricing or financial calculations
- State transition restrictions
- Validation of business operations
- Expiration or date-based policies
- Duplicate-operation prevention
- Transactional safeguards
- Domain-specific error conditions

For every rule record:

- Rule ID
- Description
- Condition or predicate
- Effect or decision
- Implementation class/method or SQL object
- Related capability IDs
- Supporting source references
- Test evidence, when available
- Confidence
- Verification status

Distinguish authorization controls from business policies, while documenting any interaction between them.

## 7. Workflow Reconstruction

Reconstruct significant user journeys by following the implemented call paths.

For each workflow identify:

- Business goal
- Actor
- Entry point
- Steps and decision points
- Involved controllers and services
- Persistent state changes
- Transaction boundaries
- Alternate and failure paths
- External data dependencies
- Supporting evidence

Generate Mermaid diagrams for major workflows.

Do not equate a sequence of web pages with a complete business workflow.

## 8. Database and External Dependencies

Analyze the application's database usage.

For every relevant SQL object identify:

- Object or table name
- Read/write/execute operations
- Mapped C# entity
- Business purpose
- Relevant source code
- Dependencies on information created outside the application, if supported by evidence

Do not invent the names or functions of inaccessible external systems.

Do not interpret database access alone as proof of ownership.

## 9. Evidence and Confidence

Use repository-relative file paths, namespaces, types, methods, and optional line ranges.

Classify confidence as `high`, `medium`, or `low`.

Classify verification as:

- `static_verified`
- `behavior_verified`
- `inferred`

Only use `behavior_verified` when the relevant behavior has been executed and observed.

Keep inferred conclusions separate from directly established facts.

## 10. Deliverables

Produce:

```text
analysis-output/customerportal/
├── application-profile.md
├── capabilities.yaml
├── entities.yaml
├── business-rules.yaml
├── workflows.yaml
├── dependencies.yaml
├── evidence-index.yaml
├── analysis-gaps.md
└── summary.md
```

Use stable identifiers including:

- `CP-CAP-001`
- `CP-ENT-001`
- `CP-RULE-001`
- `CP-WF-001`

Each capability should reference the relevant entity, rule, workflow, and evidence IDs wherever appropriate.

Ensure all YAML files are syntactically valid.

## 11. Execution Sequence

1. Inventory the permitted source projects.
2. Trace application startup and MVC routing.
3. Identify user-facing operations.
4. Reconstruct entities and persistence mappings.
5. Trace domain services and business policies.
6. Reconstruct key workflows.
7. Generate a business capability catalog.
8. Verify findings against code and available tests.
9. Produce the structured output files.
10. Summarize unknowns and evidence gaps.

Use read-only analysis. Execute existing tests only in a safe test environment.

## 12. Success Criteria

The outputs should accurately explain:

- What business functions CustomerPortal implements
- How its domains are organized
- What users can do and under which conditions
- Which entities and database objects support its behavior
- Which business rules govern operations
- What application-level dependencies exist
- What remains uncertain

Do not generate modernization recommendations.

Do not produce a portfolio overlap matrix.

Do not inspect other applications.

Begin the independent analysis.
