# Stage 2 — LegacyRetailPortfolio Semantic Reconstruction

## Role

You are a Principal Enterprise Architect specializing in business capability mapping, domain-driven design, application portfolio analysis, and software reverse engineering.

Your objective is to reconstruct the consolidated business architecture of LegacyRetailPortfolio from independently generated application analyses.

Do not modernize, rewrite, or modify the applications.

## Inputs

You have access to:

- `analysis-output/orderdesk/`
- `analysis-output/customerportal/`
- `analysis-output/fulfillmentapi/`

For the second pass, you may additionally inspect:

- `src/OrderDesk/`
- `src/CustomerPortal/`
- `src/FulfillmentAPI/`
- Relevant SQL Server DDL and stored procedures
- Relevant automated tests

You must not access ground-truth benchmark files, original architecture specifications, or intended overlap classifications.

## Phase A — Semantic Consolidation

Use only the three Stage 1 analysis outputs.

### Task 1: Build a Consolidated Capability Catalog

Identify all discovered business capabilities.

Normalize equivalent business terminology without losing application-specific distinctions.

For each capability record:

- Canonical capability ID and name
- Business description
- Business domain
- Applications implementing it
- Application-specific capability IDs
- Implementation differences
- Supporting Stage 1 evidence
- Confidence rating

Preserve the original capability IDs for traceability.

### Task 2: Classify Capability Relationships

Classify relationships as:

- `duplicate`: Substantially equivalent functionality.
- `partial_overlap`: Same business capability with different responsibilities, scope, or rules.
- `complementary`: Different capabilities contributing to a common business process.
- `shared_data_only`: Shared business entities without significant functional overlap.
- `unique`: Functionality belonging to one application.

For each classification, explain why it applies.

Never classify two capabilities as duplicates based solely on common class names, table usage, or similar API routes.

### Task 3: Reconstruct Business Domains

Identify logical business domains across the portfolio.

Map each application-specific entity to a canonical business concept where justified.

Distinguish:

- Same business entity represented through different application models
- Distinct entities with similar names
- Application-owned entities
- Shared database structures
- Cross-domain relationships

Preserve application-specific behavior and boundaries.

### Task 4: Reconcile Business Rules

Identify rules associated with equivalent or related business operations.

Determine whether they are:

- Equivalent
- Different by legitimate business context
- Potentially contradictory
- Independently implemented
- Complementary

Do not automatically recommend standardizing different rules.

### Task 5: Identify Cross-Application Workflows

Reconstruct end-to-end business workflows that appear to span application boundaries.

Describe:

- Participating applications
- Business activities performed by each
- Shared entities
- State transitions
- Dependencies
- Unknown or ambiguous transitions

Mark unverified relationships as hypotheses.

## Phase B — Source-Level Verification

After completing Phase A, inspect all three application codebases, SQL DDL, stored procedures, and relevant tests.

Verify the proposed portfolio relationships.

For every relationship:

1. Confirm source evidence in each participating application.
2. Trace relevant database read/write operations.
3. Verify business-rule differences.
4. Identify actual workflow and state transitions.
5. Check whether Stage 1 overlooked relevant functionality.
6. Assign a verification status.
7. Reject or revise unsupported relationships.

Do not silently turn hypotheses into confirmed findings.

## Required Deliverables

Create:

```text
analysis-output/portfolio/
├── portfolio-capabilities.yaml
├── capability-overlaps.yaml
├── canonical-domains.yaml
├── cross-app-dependencies.yaml
├── cross-app-workflows.yaml
├── business-rule-comparison.yaml
├── portfolio-architecture.md
├── evidence-index.yaml
└── unresolved-findings.md
```

The architecture document must contain:

- Portfolio business capability map
- Application-to-domain responsibility matrix
- Shared entity mapping
- Cross-application dependency diagrams
- Cross-application workflow diagrams
- Findings concerning unique capabilities
- Verified functional overlaps
- Unresolved architectural questions

Use Mermaid for diagrams.

Every substantive finding must reference the original Stage 1 evidence IDs and, after verification, actual source-code or SQL evidence.

## Constraints

- Do not access ground truth.
- Do not modify the applications.
- Do not invent business relationships.
- Do not collapse distinct application-specific business concepts into a single canonical entity without evidence.
- Do not propose a target architecture at this stage.
- Do not assume shared database access implies duplicate capabilities.
- Do not fabricate test execution results.

## Success Criteria

The final portfolio model should explain how independently developed applications collectively support the business, which capabilities overlap, which are complementary, which remain unique, and how business entities, policies, and workflows cross application boundaries.

Begin with Phase A, save its candidate findings, then proceed to Phase B for verification.
